Security and trust boundaries

NAWC is a local development tool, not a multi-user sandbox. Its boundaries reduce accidental reach, but configured syntax runners and the agent are intentionally capable developer tools.

Filesystem boundary

Note operations are rooted under the notebook's src directory. Source references and runnable requests are rooted under baseDir. Absolute paths and lexical traversal outside either root are rejected. Startup additionally requires baseDir to be inside a Git worktree.

Browser prototype boundary

Interactive HTML is placed in an iframe with sandbox="allow-scripts". Scripts can run inside the prototype but receive neither same-origin privileges nor permission to reach the parent editor DOM. The source editor warns about this isolation.

Process boundary

A runnable block can only run when its configured syntax adapter provides a command. The server validates the selected file path, receives argv from the adapter, and uses Execa without invoking a shell. This prevents note attributes from becoming a shell command, but the adapter's process still runs with the NAWC server user's OS permissions in baseDir.

Agent boundary

The Codex adapter defaults to workspace-write, accepts read-only as a config option, and does not expose a dangerous bypass mode. It runs in baseDir, so users should treat prompts and plugin skills as instructions to an agent that may modify the repository.

Generated-file ownership

Skill synchronization only replaces files carrying NAWC's generated header. An existing unmarked SKILL.md causes startup to fail rather than silently replacing user content.
