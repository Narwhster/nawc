Architecture and data flow

NAWC is a local web application with files as its database. A notebook project supplies a typed configuration and src/**/*.html notes; the configured Git worktree supplies source, tests, and the working directory for tools.

Startup path

  1. The nawc executable parses --config and --port.
  2. The server loads TypeScript config with Jiti and resolves baseDir.
  3. Startup verifies that the base directory is inside a Git repository and synchronizes plugin skills.
  4. Hono exposes the local API; Vite serves the React UI and a virtual module containing configured client plugins.
  5. A single Node HTTP server routes /api/* to Hono and everything else to Vite middleware.
  6. The listener binds to 127.0.0.1 on CLI port, config port, or 6292, in that order.

Note editing flow

  1. The React shell lists HTML notes and loads the selected note through the API.
  2. Tiptap parses canonical HTML plus extensions from every configured plugin.
  3. StarterKit supplies common prose editing; a custom input rule turns [[Note]] into a wiki-link node.
  4. Updates are debounced for 350 ms, serialized back to canonical custom elements, and written atomically from the UI's perspective.
  5. Chokidar emits filesystem events over SSE; the UI tells live source nodes to refresh.

Source and execution flow

A <ref> or <runnable> sends its attributes to the server. Paths are checked against baseDir. A missing syntax displays the whole file; otherwise the named adapter resolves a declaration or test. Runnable adapters return an argv array and working directory, which the server executes without a shell and returns with exit code, stdout, and stderr.

Agent flow

The prompt panel prefixes the open note path and streams provider events over SSE. The Codex provider starts codex exec --json in the configured base directory, appends the plugin skills location, and maps Codex JSONL into the small provider event protocol.
