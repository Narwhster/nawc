Coordination role

This ticket owns the full static-site effort: the build package itself plus the FAQ provider that backs the agent panel inside it. It is intentionally not split, even though it carries multiple goals, because the FAQ provider is small and tightly coupled to the build's provider configuration. We may revisit the split if implementation surfaces a real seam.

Decision: a separate package, not a NAWC plugin

The static build is shipped as a separate top-level package (likely under packages/), not as a NawcPlugin added to the notebook's plugins array. The static site is a fundamentally different mode of NAWC (no dev server, no filesystem, in-browser only), and the build pipeline wants full control over the output without having to coexist with the dev server's plugin system.

Decision: standalone CLI shipped as @nawc/site

The package ships its own binary. After installing it as a dev dependency of a notebook, the user runs npx @nawc/site build to emit the static site and npx @nawc/site preview for a local vite preview-style check before deploying. There is no nawc build subcommand and no vp build coupling — the CLI is the entry point and the package controls the entire output. The CLI uses a TypeScript loader to read nawc.config.ts and nawc-static-agent.ts.

Decision: the package builds a static site from an existing nawc notebook

The package reads an existing nawc.config.ts and the notebook's src/ directory, and emits a deployable static directory. It does not modify NAWC core, add browser-compatibility shims to the dev runtime, or duplicate NAWC's note adapter. It is a build tool, not a compatibility layer.

Decision: the static site runs fully in the browser

No filesystem, no executables (no cargo, java, tsx, vitest CLI), no server. Everything happens client-side. The bundled notebook contents plus a browser-side persistence layer are the only data the site has.

Decision: static build supports only the core and typescript plugins

The static site includes only core() and typescript(). Other plugins configured in the source notebook are not active in the build. Their <runnable> elements are transformed into <ref> blocks at build time, so the source still shows up in the rendered page but without a run button.

Decision: TypeScript runnables run in the browser via esbuild-wasm

The static site ships esbuild-wasm as a lazy-loaded dependency. TypeScript <runnable> blocks compile and execute in the browser through it. No server is involved.

Decision: SPA routing, notes are files in lightningfs

The static site is a single-page app. The SPA's data model is the lightningfs filesystem: each note is a file, the SPA determines which notes exist by listing the filesystem, and URLs map to lightningfs paths (e.g. /notes/foo reads /notes/foo.html from lightningfs). The build packages each note as a static HTML file under dist/notes/, and the SPA seeds lightningfs by fetching those files on first load. After seeding, the SPA only reads from lightningfs.

Edits write to lightningfs and persist across navigation and refresh. Routing is determined by the contents of the user's filesystem, not by the build's URL structure: renames, edits, and new files are reflected immediately. The build's only job regarding notes is to provide the initial seed; thereafter, the SPA's view of "which notes exist" comes from lightningfs.

This subsumes the earlier "edits persist with lightningfs" and "users can edit notes" decisions — both are natural consequences of notes being filesystem files.

Decision: agent panel uses a tree-walking static agent

The static site does not talk to a real LLM. The agent panel is backed by a static agent: a function the notebook author writes that turns a user prompt into a conversation tree. Each question node is a multiple-choice question asked via NAWC's question tool; each answer leads to a child node, and answer leaves are emitted as the final canned response. The provider walks the tree step by step.

The matching strategy is implicit in the tree itself: there is no "best match" computation. The function decides the root question from the prompt and the matched files, and the user chooses their path through the tree.

This is the interaction primitive, so the static agent depends on [[tickets/agent-question-tool]] being implemented first. Until the question tool actually works end to end, the static agent has no way to ask its tree's questions.

The shape of the static agent is captured by [[tickets/static-agent-probe]], which carries a runnable example and a vitest probe.

Decision: static agent lives in nawc-static-agent.ts

A notebook author adds a new file alongside nawc.config.ts, named nawc-static-agent.ts. It is a plain TypeScript module that exports a default static-agent config — not a config file in the nawc.config.ts-style schema sense. The @nawc/site build CLI reads it at build time and bakes the result into the bundle. The dev server ignores it — the author's real-LLM nawc.config.ts provider is untouched.

The file's exports are:

  • files: { match: RegExp } — a top-level regex that selects which notes flow into the function as files.
  • faq: ({ prompt, files, history }) => ConversationTree — the function that builds the tree. history is the chain of { question, chosenAnswer } steps the user has already walked through in this thread.
